# Launch Readiness Desk

A small local web app that evaluates launch readiness for a set of software
features using a policy-based rules engine. Built as a prototype to demonstrate
how Amazon Q (Quick) and Kiro can collaborate: Q performs document-grounded
analysis and generates a structured handoff; Kiro implements and verifies the
code from that handoff.

**Synthetic data only.** The fictional company "Maple Outfitters" and all
feature names, owners, and QA records are invented for demonstration purposes.
This app does not connect to any cloud service, database, or external API, and
does not deploy, approve, or send anything.

---

## What it does

`decision.py` implements a rules engine (`evaluate(row)`) that reads a feature
row and applies **POLICY-2** (approved 5 November 2026):

| Priority | Condition | Result |
|----------|-----------|--------|
| 1 | `blockers > 0` OR `security == false` OR `rollback == false` | **BLOCKED** |
| 2 | Any of `blockers / security / rollback` is `null` / missing | **UNKNOWN** |
| 3 | `blockers == 0` AND `security == true` AND `rollback == true` | **READY** |

A known failure always wins over missing evidence (Rule 1 beats Rule 2).
Evaluation is driven by field values — never by feature ID lookup.

`server.py` exposes two endpoints:
- `GET /` — serves the single-page dashboard (`index.html`)
- `GET /api/report?snapshot=a` or `?snapshot=b` — returns evaluated JSON for
  the chosen snapshot

The dashboard lets you switch between snapshots A and B, filter by status,
view per-feature reasons and evidence IDs, read informal team notes (display
only — they have no effect on any status), and copy a plain-text summary to
the clipboard.

## Architecture and role of Q / Kiro

```
Amazon Q (Quick)           Kiro IDE
─────────────────          ────────────────────────────────────
Reads uploaded docs  →     Reads Q's handoff + project files
Assesses features    →     Implements evaluate() + index.html
Reassesses on B      →     Runs check.py to verify 12/12
Compares reports     →     Adds separate unit/property tests
```

- **Q** performs document-grounded reasoning across policy files, QA snapshots,
  and team notes, and produces a structured handoff for Kiro.
- **Kiro** implements the rule engine and UI, runs automated verification, and
  keeps protected inputs unchanged.

## Install and run

```bash
# Clone (or unzip) the repository
cd aws-quick-kiro-project-tracker

# Start the local server
python3 server.py
# → Open http://127.0.0.1:8766 in your browser
# → Press Control+C to stop
```

---

## Verify the rule engine

```bash
python3 check.py
```

Expected output: `12/12 cases passed`. The checker tests both snapshots against
hardcoded expected outcomes and writes per-snapshot reports to `results/`.

```bash
python3 test_decision.py          # or: python3 -m unittest test_decision
```

Runs 41 unit and property-based tests covering every rule, edge case,
precedence rule, input-validation path, and metadata contract.

## Sample workflow

1. Upload the four files in `quick_upload/` to Amazon Q.
2. Ask Q to assess all six features under POLICY-2 using SNAPSHOT-A.
3. Kiro implements `evaluate(row)` in `decision.py` and `index.html`.
4. Run `python3 check.py` — target 12/12.
5. Start the server and browse to `http://127.0.0.1:8766`.
6. Supply `updates/05_QA_Snapshot_B.txt` to Q for the follow-up assessment.
7. Switch to Snapshot B in the dashboard to see the updated results.

## Protected inputs

`check.py` verifies SHA-256 checksums for these files before running:

- `check.py` itself
- `README.md`
- `data/snapshot_a.json`, `data/snapshot_b.json`
- `quick_upload/01_Project_Brief.txt` through `04_Team_Notes.txt`
- `updates/05_QA_Snapshot_B.txt`

The hashes detect accidental edits; they are not tamper-proof security.
Add extra tests in a separate file — never modify `check.py` or the
protected data files.

## `evaluate(row)` API contract

```python
evaluate(row: dict) -> dict
```

Input keys: `id`, `feature`, `owner`, `blockers` (int ≥ 0 or null),
`security` (bool or null), `rollback` (bool or null), `source`, `snapshot`.

Output keys: `status`, `reason`, `policy_id`, `source_id`, `snapshot`,
`execution`.

- `status` is one of `"READY"`, `"BLOCKED"`, `"UNKNOWN"`.
- `execution` is always `"none"` — this app never launches anything.
- Invalid field types (e.g. negative `blockers`, string `security`) raise
  `ValueError`.

## Limitations

- **Synthetic data.** All scenarios, company names, and QA records are
  fictional. Do not use this as a template for real launch decisions.
- **Local only.** No authentication, TLS, or production hardening.
- **Prototype.** Not evaluated for enterprise scale or real-world security.
- **READY is a recommendation, not permission to ship.**
